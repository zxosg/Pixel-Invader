# Pixel Invader — ZX Screen-to-Charset Conversion Algorithm

**Status:** Proposed corrected algorithm  
**Scope:** 256×192 ZX Spectrum screens composed of 32×24 character cells  
**Cell size:** 8×8 pixels  
**Purpose:** Represent a ZX screen as a tilemap, attributes, and a reusable custom character set

## 1. Objective

The converter replaces every 8×8 bitmap cell of a ZX Spectrum screen with a reference to a character in a custom character set.

It supports two operating modes:

1. **Existing charset mode**  
   Convert the screen using a user-supplied character set. Characters may be used only in their original orientation or may also be reused through geometric transformations.

2. **Screen-derived charset mode**  
   Construct a character set from tiles found in the screen, then convert the screen using that character set. Selection may be based on literal tile frequency or, preferably, on global reconstruction quality. Transformations may be enabled or disabled.

The output is not a standard 6912-byte `.scr` file. It is a compressed character-based representation containing:

- a tile reference for each of the 768 screen cells;
- the colour attribute for each cell;
- transformation data when enabled;
- the base character bitmap data;
- format metadata needed to decode the representation.

## 2. Input assumptions

The primary input is a valid ZX Spectrum screen:

- 256×192 binary bitmap;
- 32×24 colour-attribute cells;
- one `INK` and one `PAPER` colour per 8×8 cell;
- optional `BRIGHT`;
- normally no `FLASH`.

The bitmap bits are the authoritative source of tile shape. The algorithm must not infer foreground occupancy by dividing sums of palette indices.

If the input is supplied as a raster image rather than a decoded ZX screen, it must first be converted into a legal ZX bitmap and attribute grid. Within each cell, a pixel is classified by explicit comparison with the selected `INK` and `PAPER` colours.

## 3. Core representation

For every screen cell \(i\), extract:

- \(B_i\): an 8×8 binary bitmap represented as 64 bits;
- \(A_i\): its ZX colour attribute;
- \(p_i\): its position in the 32×24 tilemap.

Use a fixed bit order, for example:

```text
bit 63 ... bit 56 = top row, left to right
...
bit 7  ... bit 0  = bottom row, left to right
```

The exact bit order is an implementation detail, but it must be fixed, documented, and covered by encode/decode tests.

## 4. Transformations

### 4.1 Spatial transformations

When transformations are disabled, only the identity transformation is legal.

When transformations are enabled, a base character may be reused through the eight symmetries of a square:

| Code | Transformation |
|---:|---|
| 0 | Identity |
| 1 | Rotate 90° |
| 2 | Rotate 180° |
| 3 | Rotate 270° |
| 4 | Mirror horizontally |
| 5 | Mirror vertically |
| 6 | Reflect across the main diagonal |
| 7 | Reflect across the anti-diagonal |

The encoder and decoder must use exactly the same coordinate mappings. Duplicate variants of symmetric characters are removed from the search index.

### 4.2 Polarity inversion

Binary inversion is not a geometric transformation. A complemented character can be rendered without storing a second character:

```text
bitmap      = NOT bitmap
output INK  = source PAPER
output PAPER = source INK
```

The visible result is unchanged. Therefore, polarity equivalence should normally be enabled in both transformation modes and should not consume a transform bit.

For matching and charset deduplication:

\[
B \equiv \neg B
\]

provided that the colour attribute is swapped when the complemented form is selected.

## 5. Common processing pipeline

```text
1. Decode and validate the ZX screen.
2. Extract 768 binary 8×8 source tiles and their attributes.
3. Obtain a base charset:
   a. load an existing charset; or
   b. derive a charset from the source tiles.
4. Generate the legal transformed variants of every base character.
5. Deduplicate identical variants.
6. Match every source tile to the best charset variant.
7. Record base-character index, spatial transform, and polarity.
8. Correct the attribute when polarity is inverted.
9. Encode the tilemap, attributes, transformation data, and charset.
10. Decode the produced representation into a verification preview.
11. Report reconstruction error and memory usage.
```

The preview must be generated by decoding the final encoded output. This guarantees that the preview represents what a ZX program would reconstruct.

## 6. Mode 1 — Existing charset

### 6.1 Purpose

This mode maps the screen to a charset supplied by the user. It is appropriate when:

- the program already has a fixed visual vocabulary;
- the same charset will be reused across several screens;
- character codes have semantic meaning;
- compatibility with an existing engine is required.

### 6.2 Algorithm

1. Load \(N\) base characters, each containing eight bitmap bytes.
2. Validate the character count against the chosen output encoding.
3. For every base character:
   - generate the identity only when transformations are disabled;
   - generate all eight square symmetries when transformations are enabled;
   - consider both normal and complemented polarity;
   - remove duplicate variants.
4. For each of the 768 source tiles:
   - compare it with every legal charset variant;
   - choose the variant with the lowest matching cost;
   - store its base-character index and transform code;
   - if complemented polarity won, swap `INK` and `PAPER` in the output attribute.
5. Encode the result and create a decoder-generated preview.

### 6.3 Deterministic tie-breaking

When two candidates have equal cost, select in this order:

1. exact pixel match;
2. non-inverted polarity;
3. identity transformation;
4. lower transform code;
5. lower base-character index.

This avoids arbitrary changes between runs.

## 7. Mode 2 — Screen-derived charset

### 7.1 Purpose

This mode derives a charset specifically for the current screen. The resulting charset should represent all 768 source tiles as accurately as possible within a selected character budget \(N\).

### 7.2 Exact-frequency baseline

A literal “most-used tiles” implementation is:

1. Canonicalize every source tile under the enabled spatial transformations and polarity inversion.
2. Group equivalent tiles.
3. Count occurrences of every canonical tile.
4. Sort the groups by descending frequency.
5. Select representatives of the first \(N\) groups.
6. Map all source tiles to the nearest selected representative.

This is a valid fast baseline, but it is not the recommended final method. It can spend several character slots on similar shapes while leaving less common but visually important shapes poorly represented.

### 7.3 Recommended global dictionary selection

The charset should be selected as a complementary dictionary, not as \(N\) individually common or average tiles.

Let:

- \(U=\{u_1,\ldots,u_m\}\) be the unique canonical source tiles;
- \(f_i\) be the number of occurrences of \(u_i\);
- \(w_i\) be an optional visual-importance weight;
- \(d(u_i,c)\) be the best matching cost between source tile \(u_i\) and candidate character \(c\), considering all enabled transformations and polarity;
- \(S\) be the selected base charset.

For a fixed character count \(N\), select:

\[
\boxed{
S^*=\arg\min_{S\subseteq U,\;|S|=N}
\sum_{i=1}^{m} f_iw_i\min_{c\in S} d(u_i,c)
}
\]

This is a weighted, transformation-aware **k-medoids/facility-location** problem. Restricting \(S\) to source tiles ensures that every selected character genuinely comes from the screen.

### 7.4 Practical selection algorithm

Use greedy facility-location selection followed by swap refinement:

```text
INPUT:
    unique source tiles U
    occurrence/importance weights W
    requested character count N

PRECOMPUTE:
    distance[i][j] =
        best structural distance from source tile i
        to candidate base tile j under legal transformations

IF count(U) <= N:
    select all unique canonical tiles
    conversion is lossless
ELSE:
    1. Select the first candidate that gives the lowest total weighted error.
    2. Record each tile's distance to its nearest selected candidate.
    3. Until N candidates are selected:
         choose the candidate that produces the largest reduction
         in total weighted reconstruction error;
         update all nearest-candidate distances.
    4. Perform local refinement:
         try replacing each selected candidate with each unselected candidate;
         accept the best improving swap;
         repeat until no swap improves the objective or the search budget ends.
    5. Assign every screen tile to its best selected character variant.
```

This method naturally balances frequent patterns with coverage of shapes that are different from everything already selected.

### 7.5 Optional visual weighting

The basic weight is the tile occurrence count. A quality-oriented mode may additionally weight each occurrence by:

- `INK`/`PAPER` contrast;
- local edge importance;
- source-region saliency;
- whether the cell contains a rare thin feature.

Low-contrast pattern errors are then allowed to matter less than the loss of a high-contrast contour. This weighting must be optional because a purely shape-based charset may be preferable when the charset will be reused with different colours.

## 8. Improved pattern matching

### 8.1 Why the original matcher is insufficient

The macro reduces every 8×8 tile to sixteen 2×2 occupancy counts and compares them with:

\[
D_{\text{old}}(A,B)=
\sum_{k=1}^{16}|o_k(A)-o_k(B)|
\]

This descriptor is useful as a coarse summary, but it discards the position of pixels inside each 2×2 block. Diagonal, checkerboard, corner, and line patterns can therefore receive an identical score despite looking different.

### 8.2 Recommended structural distance

Compare transformed candidates using a hybrid binary-shape metric:

\[
D_{\text{shape}}
=
\alpha D_{\text{pixel}}
+\beta D_{\text{near}}
+\gamma D_{\text{edge}}
+\delta D_{\text{mass}}
\]

where every component is normalized to \([0,1]\):

- **\(D_{\text{pixel}}\): full-resolution Hamming distance**  
  `popcount(A XOR B) / 64`. This preserves every pixel and strongly rewards exact matches.

- **\(D_{\text{near}}\): symmetric chamfer distance**  
  Measures how far unmatched foreground and background pixels must move to overlap. A one-pixel-displaced line is penalized less than a completely unrelated pattern.

- **\(D_{\text{edge}}\): edge-map mismatch**  
  Compare horizontal and vertical transitions in both tiles. This protects thin lines, corners, diagonals, and silhouettes.

- **\(D_{\text{mass}}\): density and centroid difference**  
  Compare foreground pixel count and its centre of mass. This discourages matches with incorrect overall weight or position.

A practical starting configuration is:

```text
alpha = 4
beta  = 2
gamma = 2
delta = 1
```

The weights should later be tuned against a representative ZX image corpus.

### 8.3 Fast implementation

For a compiled or browser implementation, an exhaustive comparison is practical:

```text
768 screen cells × at most 256 characters × at most 8 transforms
```

Most of the work uses 64-bit XOR, population count, and table lookups.

For an ImageJ macro implementation:

1. Use foreground count, 2×2 occupancy, and edge count to shortlist the best 8–16 variants.
2. Apply the full structural metric only to the shortlist.
3. Cache all pairwise unique-tile distances in screen-derived mode.

The old 4×4 occupancy descriptor is therefore retained as a search accelerator, not as the final quality measure.

### 8.4 Alternative lightweight matcher

If chamfer distance is too expensive, use a multi-scale bit metric:

\[
D_{\text{lite}}
=4D_{\text{Hamming}}
+2D_{\text{2×2 occupancy}}
+D_{\text{4×4 occupancy}}
+2D_{\text{edge}}
\]

This is substantially better than the original matcher while remaining easy to implement using integers.

## 9. Output encoding

The logical output contains:

| Section | Content |
|---|---|
| Header | Version, dimensions, character count, flags, section sizes |
| Tilemap | 768 base-character references |
| Attributes | 768 ZX attribute bytes |
| Transform data | Spatial transform for each cell, when enabled |
| Charset | \(N \times 8\) bitmap bytes |
| Optional diagnostics | Error score, exact-match count, source hash |

### 9.1 Compact legacy mapping

A single byte may contain:

```text
bits 7–3 = character index, 0–31
bits 2–0 = spatial transform, 0–7
```

This supports at most 32 base characters. Polarity remains represented by swapping `INK` and `PAPER`.

### 9.2 Extended mapping

To support up to 256 characters with transformations:

- store one byte per base-character index; and
- store transform codes in a separate plane.

The transform plane may use:

- one byte per cell for fast decoding; or
- packed 3-bit codes for lower memory use.

The format must not expose a 256-character slider while using a five-bit character field.

## 10. Memory and quality reporting

Report at least:

- base charset size: \(8N\) bytes;
- tilemap size;
- attribute size;
- transform-data size;
- header size;
- total output size;
- exact cell matches;
- average and maximum structural error;
- count of polarity swaps;
- transform usage histogram.

When comparing transformed and untransformed modes, compare total representation size—not only charset size. Transform metadata and decoder complexity are part of the trade-off.

## 11. Validation requirements

The converter must verify:

1. Input dimensions are multiples of 8; standard mode requires 256×192.
2. Exactly 768 cells exist in standard mode.
3. Every input tile has a valid bitmap and attribute.
4. Character count fits the selected reference encoding.
5. Every emitted character index is within range.
6. Every transform code is legal.
7. The encoded charset contains exactly \(N \times 8\) bytes.
8. Decoding the output reproduces the displayed preview exactly.
9. A lossless result is produced when all unique canonical tiles fit within the character budget.
10. Transformations never change the intended visible `INK` and `PAPER` placement.

## 12. Recommended implementation priorities

1. Implement exact 64-bit tile extraction and reconstruction.
2. Define and test all eight spatial transforms.
3. Implement polarity normalization through attribute swapping.
4. Implement Mode 1 using Hamming distance as a correct baseline.
5. Add the hybrid structural matcher.
6. Implement Mode 2 frequency selection as a baseline.
7. Replace frequency-only selection with greedy transformation-aware k-medoids.
8. Add swap refinement.
9. Implement both compact and extended output layouts.
10. Validate every conversion by decoding the produced output.

## 13. Recommended final behavior

The product should expose two clear choices:

```text
Charset source
    • Existing charset
    • Derive from this screen

Character reuse
    • Original orientation only
    • Allow rotations and reflections

Derived-charset strategy
    • Most frequent — fastest and literal
    • Best coverage — recommended

Character budget
    • 1–256 without packed transforms
    • 1–32 with legacy packed transforms
    • 1–256 with extended transform data
```

The recommended default is:

> **Derive from this screen + Best coverage + transformations enabled**

This gives the smallest useful charset for a chosen quality level and avoids wasting character slots on patterns that are frequent but mutually redundant.
